# 2026-04-22 会话纪要：编辑模式 / 浏览模式一体化迭代

## 背景

本轮会话聚焦两条主线：

- 让 `studio/` 的编辑模式继续向真正可用的 Prompt CMS 靠拢
- 让 `src/` 的正式浏览模式在视觉和结构上与编辑模式统一

同时，这次迭代也暴露了一个重要现实：**只靠“代码能 build”并不足以说明浏览体验正确，尤其是编辑模式与浏览模式并行演进时。**

## 本轮完成的核心结论

### 1. Prompt CMS 的真实定位进一步明确

`studio/` 不应被理解为传统 CMS 表单，而应被理解为：

- 面向 `Capsule` / `Issue` 的本地编辑器
- 面向 `workbench/inbox/` 的操作单生成器
- 面向 Copilot 的 prompt 预处理器

也就是说：

- 编辑器负责生成待执行意图
- inbox 负责承接待执行操作
- Copilot 负责读取、分析、预览、发布与归档

### 2. 浏览模式不能只做“视觉接近”

这次确认了一个重要经验：

如果浏览模式的结构、交互和内容编排模型仍然沿用旧架构，只做一些颜色和边距调整，那么最终效果仍会与编辑模式割裂。

因此浏览模式必须同时统一三件事：

- 页面骨架：三栏结构
- 内容模型：Issue / Capsule / link / image / note / capsule-ref
- 视觉语言：Header、Tabs、卡片、Tag、图片比例、链接块、状态感

### 3. Capsule 列表视图必须有单独的“预览渲染”策略

当 Capsule 取消标题展示后，如果列表仍直接渲染完整正文，卡片会立刻失去节奏感。

因此本轮确认：

- 列表卡片使用 preview render
- 详情/展开态才使用完整 render
- 预览最多展示有限正文与最多一个额外媒体/链接提示

### 4. Slash 命令插入依赖同步用户手势

`/image` 与 `/link` 弹窗失效的根因不是数据模型，而是调用时机。

经验教训：

- `window.prompt()` 一旦被异步包装，很容易失去受信用户手势上下文
- slash 命令触发图片/链接插入时，应尽量同步执行

### 5. 浏览页存在“合法代码但高风险交互结构”问题

本轮还确认了一个很关键的前端经验：

- 即使静态检查和构建都通过，运行时仍可能因为不安全的 DOM 结构出现异常或不可预期表现

具体例子：

- 内嵌 Capsule 曾经使用“外层 button，内层再嵌 button / link”
- 这种结构虽然不一定每次都直接白屏，但属于高风险无效交互结构

本轮已将其改为非嵌套式可点击容器。

## 本轮设计调整

### 编辑模式

- Issue 标题支持在编辑器和卡片编辑态中直接修改
- Capsule 卡片不再展示标题，保留正文和块内容
- 卡片操作按钮收口到底部右侧，与 Tag 区共存
- Tag 区允许折行，避免与操作按钮冲突
- 支持链接块视觉样式和 `/link` 插入
- 支持图片块和链接块的本地预览、编辑和 lightbox
- 样式设置抽屉按“通用 / Capsule 专属 / Issue 专属”重新组织

### 浏览模式

- 改为左 Tabs / 中内容 / 右搜索与标签的三栏结构
- Header 改为和编辑模式同一视觉语言
- 本地 `/browse` 保留“编辑模式”返回按钮；线上不显示
- 中间列只展示已发布内容，不承担编辑职责
- Issue / Capsule 卡片改用与编辑模式一致的间距、配色、链接块、图片比例和块级节奏
- Issue 中嵌入 Capsule 改为整体卡片可点击，不再保留“独立查看”按钮

## 这次暴露出的流程问题

### 0. 这次“白屏”排查被拖长的直接根因，是验证了错误运行时

这轮最浪费时间的问题，不是某一行 React 代码，而是：

- 用户实际在看 `http://localhost:4318/`
- 调试阶段一度主要验证的是 `4322` 与 `4173`
- `4318` 当时跑的是旧版 `node` 进程，不是当前仓库最新服务

结果就是：

- 代码已经修到新进程里了
- 用户浏览器却还在看旧进程输出
- 双方看到的根本不是同一个运行时

这类问题比普通 bug 更危险，因为它会制造一种错觉：

- “我这里明明好了”
- “你那里明明还坏着”

两边都没说错，但讨论对象不是同一个服务实例。

因此后续必须把下面这条写成硬规则：

- 先确认用户实际访问的端口、路径、进程，再开始判断前端是否修好

### 1. 只做 build 验证不够

本轮出现了“用户感知页面空白，但构建通过”的信号。虽然最终本地复现中 `/`、`/browse/` 和 CMS 根页都能渲染，但这说明我们需要把验证流程升级成：

- 静态检查
- 构建检查
- 本地真实页面验证
- 至少覆盖编辑模式与浏览模式两个入口

### 2. 浏览模式和编辑模式必须成对验收

只验一个入口会漏掉另一边的结构或路径问题。

以后涉及双端联动的改动，至少验证：

- `http://localhost:<cms-port>/`
- `http://localhost:<cms-port>/browse/`
- `vite preview` 或 `npm run dev` 下的正式浏览页

并且要额外确认：

- 当前监听该端口的进程，是否真来自当前仓库
- 当前端口返回的页面标题/关键文案，是否符合本轮代码版本

### 3. 要把“会话结论”快速回写到文档

这次如果不记录，很多关键经验会丢失，例如：

- Prompt CMS 的真实定位
- preview render 的必要性
- slash 弹窗必须同步执行
- 浏览模式必须结构性统一而不是表面统一

所以本文件本身就是流程升级的一部分。

- `studio/` 编辑模式能在本地 CMS 下渲染出内容

- 为浏览页路由初始化补充 `window` 防御

- 修正内嵌 Capsule 的交互容器，避免按钮嵌套按钮/链接

- 以后同类问题仍可能以浏览器缓存、入口路径、旧服务未重启等形式再次出现
- 因此后续还需要补更严格的手工验收与入口检查清单

## 对后续协作的要求

如果未来继续迭代 Prompt CMS 与浏览模式，默认应遵守以下规则：

1. 先确认改动影响的是 `studio/`、`src/` 还是两者
2. 若两者都受影响，必须同步验证两个入口
3. 不接受只改样式、不改结构却声称“统一体验”的方案
4. 出现运行时问题时，不能只依赖 build 结果，必须检查真实页面
5. 会话中形成的新认知，需要回写文档，而不是只留在聊天上下文里
